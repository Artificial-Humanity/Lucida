## 🔴 High (new)

### HN1 — The binding mask is described as "advisory" on every agent-facing surface; only README.md was updated

v0.9.0 (`cd3c9a9`) made the ComfyUI mask **binding**: Lucida builds the inpaint graph
and composites the render back through the mask, measured at **0.00/255 change outside
it** — the guarantee no hosted provider offers, and the release's headline feature. The
README was updated to say exactly that (README §"Two providers accept a mask, and they
mean different things by it"), and `openai.rs` grew a test that frames the question
perfectly (*"the set of masking providers changed; is the new one advisory or binding?"*).

Every other surface still tells the old story. Confirmed in the working tree:

1. **`src/main.rs:105`** — the `--mask` clap help: *"openai only, and advisory"*. Wrong
   twice: comfyui also masks, and its mask is binding. A CLI user reading `--help` will
   not even try `--mask` on comfyui — the feature v0.9.0 shipped is invisible from the
   surface most people read first.
2. **`src/main.rs:868`** — `lucida models` prints `mask  accepted (advisory)` for every
   provider with `caps.mask`, comfyui included.
3. **`src/mcp.rs:200`** — the `generate_image` tool description interpolates the provider
   list but hand-writes the semantics: *"(comfyui, openai, advisory)"*.
4. **`src/mcp.rs:276`** — the `mask` parameter description: *"ADVISORY, not binding …
   Composite over the original if untouched pixels matter."* On comfyui Lucida already
   composites — the instruction sends an agent to redo, badly, what the render provably
   did (0.00/255).
5. **`src/mcp.rs:600`** — the `image_providers` probe: `mask: accepted (advisory)`. This
   is the sharpest instance, because the skill's whole design is *"believe the probe"* —
   capability facts were exiled from the skill so that one always-current place answers
   them, and that place now answers wrongly.
6. **`src/provider.rs:388`** — the refusal when a provider cannot mask: *"Use the
   `openai` provider, which does"*. It omits comfyui — the only provider whose mask
   actually guarantees anything, i.e. the better remedy.
7. **`skills/lucida/SKILL.md:90`** — *"A mask, where supported, is advisory rather than
   binding. … composite the result back over the original yourself."* The skill ships
   inside every binary via `include_str!`, so v0.9.0 shipped a feature and the
   contradiction of that feature in the same file set.

This is the 2026-08-02 review's headline failure mode recurring on schedule — that
review predicted the hand-written surfaces would rot "when provider six lands"; they
rotted when a *capability changed kind* instead. The mechanism is precise:
`Capabilities.mask` is a `bool`, so the advisory/binding distinction *cannot* be
generated — the moment mask semantics forked, every surface holding the word "advisory"
became hand-maintained prose, and none of them was in the update path of the commit that
forked it.

**Recommendation (systemic, same shape as the provenance fix):** make mask a three-state
enum (`No` / `Advisory` / `Binding`) with a `describe()`, exactly like
`Provenance::describe()` which already feeds every surface correctly. Then
`lucida models`, both `mcp.rs` sites, and the refusal remedy are generated and cannot
disagree; the clap literal and SKILL.md line get corrected by hand (clap attribute
strings must be literals — known §5.1 surface) — the skill should say the *semantics
differ per provider and the probe states which*, which is a stable sentence. The
`exactly_two_providers_mask_and_they_differ_in_kind` test then asserts the enum values
rather than a comment. Also worth adding: the skill's ban-list tests block provider
names and counts but not semantics claims — a ban on "advisory"/"binding" in SKILL.md
would have caught this at commit time.

## 🟠 Medium (new)

### MN1 — The config file is unreachable on stock Windows, and CI structurally cannot see it

`config.rs`'s `home()` reads **only `HOME`** (`src/config.rs:264`), while the two new
modules in this very range both read `HOME` *or* `USERPROFILE` (`update.rs:473`,
`setup.rs:316`). On stock Windows — PowerShell, cmd, or a GUI-launched Claude desktop
app spawning `lucida mcp` — `HOME` is unset, `XDG_CONFIG_HOME` is unset, so
`search_paths()` returns an empty list: no config file is ever found, `config --init`
and `--set` have nowhere to write, and the exact case the config file exists to solve
(the GUI-launched MCP server that inherits no shell) is the case that fails.

Until this range that was academic. This range shipped `install.ps1`, a Windows release
asset, Windows self-update, and a Windows CI lane — Windows is now a first-class
platform whose users cannot file a key.

**Why CI passes anyway:** the Windows CI job runs `scripts/smoke.sh` under bash
(`defaults: run: shell: bash`), and git-bash/MSYS *sets* `HOME`. The smoke checks that
"the config file is read with no environment" pass in an environment no native Windows
user has. The gap is invisible to exactly the machinery built this range to catch
platform differences.

**Recommendation:** one line — `home()` falls back to `USERPROFILE` like its two
siblings (or, more idiomatically, `%APPDATA%\lucida\config.env` joins `search_paths()`
on Windows). Consider a small native-PowerShell config check in the Windows CI lane,
since bash-on-Windows cannot represent this class.

### MN2 — `lucida setup` cannot detect Claude Code on Windows

`setup.rs`'s `which()` (`src/setup.rs:322`) joins the bare name against each `PATH`
entry and tests `is_file()`. On Windows the executable is `claude.exe` or `claude.cmd`
(per `PATHEXT`); the bare-name file does not exist, so detection fails, the Claude Code
steps and the skill write are silently skipped, and on a machine without the desktop app
`setup` reports *"found neither Claude Code nor the Claude app"* while `claude` runs
fine in the same terminal. The module docs honestly say only macOS was verified — but
the subcommand ships everywhere the binary does, including through `install.ps1`.

**Recommendation:** consult `PATHEXT` on Windows (or probe the two conventional
extensions explicitly). The candidate-name construction is a pure function a test can
pin per-platform, same as `asset_name` already does in `update.rs`.

## 🟡 Low (new)

### LN1 — `merge_desktop_config` rewrites the user's desktop config non-atomically

`src/setup.rs:266` writes `claude_desktop_config.json` with a truncating `fs::write`.
A crash or full disk mid-write destroys a file the module's own doc comment promises to
treat gently ("a tool that rewrites someone's preferences … has done considerably more
than it was asked to") — and it holds *other* servers' registrations, not just Lucida's.
`update.rs`'s `install_over` already demonstrates the house pattern: stage next to the
target, then rename. Same applies, at lower stakes, to `set_config`/`remove_config` on
`config.env` (which holds API keys; the `--set` half predates this range).

### LN2 — `merge_desktop_config` panics on a malformed `mcpServers`

`config["mcpServers"]["lucida"] = …` (`src/setup.rs:259`) auto-creates objects through
`Null`, but if an existing config holds `"mcpServers": []` (or any non-object),
serde_json's `IndexMut` **panics** instead of producing the polite error the
not-an-object case just above it gets. One `is_object` check on the key first.

## 🔵 Verified good

Worth recording so future reviews need not re-derive it:

- **The seed fix (`069f72d`) is correct and correctly diagnosed.** Clock read once per
  process, `AtomicU64` counter supplies intra-process distinctness, MMIX multiplier
  scatters adjacent tickets; the macOS 1 µs / Linux 1 ns analysis explains exactly why
  this survived five releases. The 1000-seed batch test makes the assertion
  platform-independent, and the scatter test pins the low-bits property Flux needs.
- **The mask graph does all three things at once, and the tests know it.** Conditioning
  through `InpaintModelConditioning`, sampler fed from the inpaint latent, save fed from
  the composite — each pinned individually, the no-mask case pinned to contain none of
  it, the mask scaled to the *scaled* source, alpha convention verified against a live
  server, uploaded over HTTP so remote ComfyUI needs no shared mount.
- **`--workflow` + `--mask` cannot silently drop the mask** — verified unreachable by
  construction: a mask requires `reference_images` (`provider.rs:396`), and a workflow
  refuses reference images (`comfy.rs:768`). The interlock holds from both CLI and MCP.
- **`update.rs` keeps every promise it makes.** Check installs nothing (wire-tested,
  one request); Ask without a terminal refuses before downloading (wire-tested); the
  cargo reinstall is pinned `--tag` so it installs what was offered; the asset name is
  pinned against `release.yml` by test; the checksum's integrity-not-provenance limit is
  stated where it is checked; the notice stamp is written *before* the request so a down
  GitHub costs one attempt a day; opt-out is a `KNOWN_KEYS` citizen; the Windows
  rename-aside dance rolls back if the second rename fails.
- **`release.yml` and the updater agree on `{asset}.sha256`** — per-asset checksum files
  on all three platforms, `sha256sum`/`shasum` line format matching `verify()`'s parse.
  The static-linkage check now actually asserts (`static-pie` accepted, `ldd`
  confirmed) instead of pattern-matching itself into a no-op.
- **Both installers refuse the classic pipe-to-shell hazards**: everything in a
  function called on the last line, checksum verification mandatory with no skip flag,
  unknown platforms error toward the releases page, PATH advice printed rather than
  profiles edited. CI runs both against the live release on all three platforms,
  including the pinned-version path — the installers' asset names are a hand-written
  list, and that job is what keeps them honest.
- **The precedence reversal is complete and displayed.** `origin_of` pins the table
  in-process; smoke pins it end-to-end in a fresh process with `env -i`; shadowed
  environment values are named; the retired `GOOGLE_API_KEY` is diagnosed only while
  load-bearing (silent once `GEMINI_API_KEY` is set — asserted in both directions);
  `--set` refuses the retired name; `--remove` edits the file *in use* rather than the
  preferred path, and says so when an environment value un-shadows. The template
  round-trips through the parser as a no-op.
- **The skill's design is right even though HN1 dented it.** `include_str!` makes the
  repo file the shipped file; the frontmatter, name-ban, count-ban, and LF tests are
  exactly the right shape — the ban list needs a *semantics* entry (HN1), not a rethink.
  The CRLF story (`.gitattributes` + the tolerant line-based test + the `\r` tripwire)
  is a model writeup of a platform bug.
- **CI closes the gap the seed bug exposed**: three-OS test matrix, tests provably
  offline (testserver on loopback), clippy at `-D warnings`, smoke against the built
  binary, and the installer jobs above.
